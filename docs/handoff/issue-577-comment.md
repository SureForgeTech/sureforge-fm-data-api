**One acceptance criterion above was wrong and is corrected here.** It read "The shipped template's version marker and the extension's shipped-source hash list are updated for the changed template sources." That was written before the facts were checked. The three runtime files this change touches carry no `fmweb-managed` marker and are not in the extension's `MANAGED_TEMPLATE_FILES`, `SHIPPED_MARKED_HASHES` or `SHIPPED_SHARED_HASHES`, so **no template version bump and no hash entry are owed** — the generator copies an unmanaged file verbatim, and an app generated by an earlier extension version keeps its old copy. The shipped-source hash list is therefore unchanged, and still correct.

The corrected criteria:

- Each of the strings listed above reads the same for an event registration form and for a feedback or request form.
- The private preview still shows the same states, messages and safety behaviour.
- The extension's shipped-source hash list is unchanged and still correct, and the shipped template still matches the sources.
- The repository's full gate passes.

## What the change does not touch, and why

- The session-storage key `fmweb.registration.v1.…` names the duplicate-protection state, so renaming it would silently discard that state. A comment now says so where it is used.
- The bridge route `/submitRegistration` and the environment variable `FMWEB_REGISTRATION_MODE` are protocol constants shared with the extension's bridge server, not user-visible wording. A comment now says so where the route is used.
- The event registration starter's own copy, the legacy **Build a Portal** command, the receipt-ledger diagnostics and the "registration notes" matching synonym name the event registration starter or an internal protocol, so they keep their wording.
